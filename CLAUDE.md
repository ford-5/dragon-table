# D&D App — Project Guide for Claude

## About this project
A web app for playing Dungeons & Dragons, built step by step as a **learning project**.
The person building it is a beginner who is learning to code through this project.

## How to help (most important)
- **Teach, don't just build.** Explain new concepts in plain language before writing code.
- **Small steps.** Add one feature at a time so each change is easy to understand.
- **Explain the code.** After writing code, walk through what each part does.
- **Offer a small challenge** at the end of each step to practice on their own.
- **No jargon without a definition.** If a technical term comes up, explain it briefly.
- Ask before adding new tools, libraries, or frameworks.

## Tech choices (for now)
- Plain **HTML, CSS, and JavaScript** — no frameworks, no build tools yet.
- Most pages work by opening them in a web browser. For the full app run `ruby server.rb` (see "Running the app").
- Save data in the browser with `localStorage` when needed.
- Two additions, both approved by the user: **PeerJS 1.5.4** (MIT, loaded from unpkg, pinned) for live games, and a small **Ruby helper server** (`server.rb`, Ruby ships with macOS) that holds the Anthropic API key for the AI Dungeon Master.
- Later (only when ready): Git, then possibly React.

## Running the app
- Just the pages (no AI): open `index.html` from Finder, or `ruby server.rb` and go to http://localhost:8787 (recommended: all pages then share saved data).
- With the AI Dungeon Master: the USER types their own key in Terminal (never ask for it or put it in any file or chat):
  `cd ~/Documents/dnd-app`, `export ANTHROPIC_API_KEY="..."`, `ruby server.rb`, then open http://localhost:8787
- Players on the same Wi-Fi: `ruby server.rb --share` prints the Wi-Fi address. The AI endpoint still only answers requests from the computer running the server.

## The app is based on real D&D rules
Everything that is a game rule lives in `rules.js` and follows the SRD 5.2.1 (the 2024 rules).
Pages should **calculate** from the rules (modifiers, proficiency, HP, AC, saves, skills), never ask the player to type a number the rules can work out.

## The flow (start screen)
`index.html` (**Player**, **DM**, or **Equipment** → `equipment.html`, the shop).
- **Player** → `player.html` (**AI Dungeon Master** or **Live Dungeon Master**).
  - **AI** → `ai-dm.html`, five steps that unlock one at a time: 1) help level (Beginner / Intermediate / Advanced), 2) hero (pick one, or "Create a new hero" → `character.html?guide=<level>&return=ai-dm.html`, which comes back as `ai-dm.html?hero=<id>`), 3) campaign (setting, kind of story, one-shot or campaign, extras), 4) special item (list or custom; saved onto the hero's sheet), 5) Begin.
  - **Live** → `join.html`: code + hero → a **waiting room** that checks for the DM every 5 seconds for up to 30 minutes, so players can arrive before the DM opens the game.
- **DM** → `dm-start.html` (**Learn to be a DM** → `dm-learn.html`, or **Run a game** → `dm.html`). `dm.html` has Request players (with voice chat), the Battle Simulator link (`battle.html`), party, initiative, notes and the rulebooks.

- `index.html` — the **start screen**: "I'm a Player" / "I'm the Dungeon Master".
- `player.html` — the **player hub**: choose AI Dungeon Master or Live Dungeon Master (and links to characters and dice).
- `ai-dm.html` — **AI Dungeon Master** (solo play): the five setup steps above, then chat. The chosen help level is remembered in `localStorage` key `"playerGuide"` and saved on the adventure (`adventure.guide`); the campaign is saved on the adventure (`adventure.campaign`) so Continue keeps it. The request to `/api/dm` carries `character`, `campaign` (text built by `makeCampaignText`), `guide` (just the level's name) and `messages`. `server.rb` turns the level into teaching instructions from its own `GUIDE_NOTES` table (the page can't write them): Beginner = the DM explains rules in one plain sentence, says why a roll is needed, and ends with 2–3 ideas; Intermediate = short reminders for uncommon rules; Advanced = no tutorials. Beginners also get a "How to play" box (open at the start of a story). Players roll with their real sheet bonuses (checks, saves, skills, item Advantage) into the message box. One adventure per hero is saved in `localStorage` key `"aiAdventure-<heroId>"`. Shows setup instructions when the helper server or key is missing. Messages and the hero's sheet are sent to Claude through `server.rb`.
  - **AI tags**: `DM_INSTRUCTIONS` in `server.rb` tells the AI to end replies with `[ROLL: Perception]`, `[ROLL: Dexterity save]`, `[ROLL: 1d20+5 attack]`, `[ROLL: 2d6+3 damage]`, optionally "with advantage/disadvantage", and `[MUSIC: calm|tavern|exploration|mystery|danger|battle|victory]` when the mood changes. Messages are stored with tags (so the AI sees its own history) but `stripDmTags()` hides them when shown or read aloud. `play.js` has `findRollRequest` (tag first; if missing, a guess from "… check"/"… saving throw" in the last ~220 characters), `findMusicTag`, `describeRollRequest`, `rollRequest`. Unknown skills or moods are ignored.
  - **Ready-to-roll button**: when the latest DM message asks for a roll, a dashed box under the chat shows e.g. "🎲 Roll Perception (+2)" with the sheet's bonus (item Advantage included) or the DM's dice; one click rolls and sends it (plus anything typed). The normal roll dropdowns are set to match.
  - **Scene music** (`music.js`, Web Audio, no files): 7 mood recipes (key, scale, tempo, chord loop, instruments, bass and drum styles), composed live and endlessly; crossfades between moods; master volume with a compressor. Page: 🎵 Music on/off (remembered in `"aiMusic"`; starts on the Begin/Continue click if it was on), mood label, volume slider; the music ducks to about a third while the DM is read aloud. The mood is tracked even while the music is off. Tested by rendering every mood with an `OfflineAudioContext` (continuous sound, no clipping) and a mid-render mood switch, not by listening.
  - **↩ Redo my move**: shown under "…the Dungeon Master is thinking" only while the answer hasn't arrived. It cancels the request (`AbortController`), removes the player's message, and puts it back in the box to edit; a late answer to a cancelled request is ignored (`currentRequest` check), so the player never sees it. Not offered for the opening "Begin the adventure" message or for any move containing a dice roll (🎲), so bad rolls can't be taken back. (The helper server may still finish the cancelled call, which costs a little API usage.)
  - **Voice** (browser built-ins, no library; this is the AI page's read-aloud and voice typing, separate from the live DM–player voice chat): each DM message has a 🔊 Read aloud / ⏹ Stop button (`speechSynthesis`, read one sentence at a time because some browsers stop long text halfway; voice matched to the browser language), plus a "Read new replies aloud" checkbox remembered in `localStorage` key `"aiAutoRead"`. 🎤 Speak your reply uses `SpeechRecognition` / `webkitSpeechRecognition` (Chrome, Safari; hidden with a note elsewhere): words appear in the box as you speak, added to what's typed, never sent automatically; listening stops the DM's voice first. Errors (blocked mic, no speech, no internet) get plain messages. The page tells players that voice typing may send audio to Google (Chrome) or Apple (Safari). Tested with recorded speech calls and a pretend microphone, not real audio.
- `join.html` — **Live Dungeon Master** (player side): enter the DM's 6-character game code, pick a hero, "Go to the waiting room". With no characters, "Create a character" goes to `character.html?return=join.html` and back with the hero picked; the typed code is kept in `sessionStorage` key `"joinCode"`; the hero list refreshes on the `storage` event (hero made in another tab) and on `pageshow` (Back button). (The waiting room retries on `peer-unavailable` every 5 s, gives up after 30 min; "Stop waiting" button). When accepted: table feed, DM-kept HP (also written to the saved sheet), rolls and messages shared with the DM, "Send my updated sheet" (also automatic when the sheet changes in another tab). `?code=ABC123` in the URL pre-fills the code.
- `server.rb` — the **helper server** (Ruby, no gems). Serves the pages (only .html/.js/.css/.png/.svg/.ico, no dotfiles, no path traversal) and `POST /api/dm` (the AI) + `GET /api/status`. The AI endpoint: loopback clients only, `Host` must be localhost, `Origin` must be its own page (blocks other websites and DNS rebinding), JSON only, 200 KB cap, max 20 replies/minute, validated conversation shape. Calls the Messages API with raw HTTP (macOS's Ruby 2.6 can't run the Ruby SDK): model `claude-opus-5-5` (env `AI_DM_MODEL` overrides), `output_config.effort: "low"`, `fallbacks: "default"` with beta `server-side-fallback-2026-07-01` (env `AI_DM_NO_FALLBACKS=1` turns it off), `anthropic-version: 2026-10-21`, no `thinking`/`temperature` params, refusals handled. The DM persona prompt lives in `DM_INSTRUCTIONS` there. Env `AI_DM_UPSTREAM` points it at a fake API for testing.
- `play.js` — shared helpers for play: `getCheckList` / `rollCharacterCheck` / `fillCheckSelect`, `makeSheetText` (the sheet as text for the AI; leaves out the player's real name and inventory notes), live-game helpers (`getClientId`, `makeGameCode`, `normalizeCode`, `peerIdFromCode`, `makeSharedCharacter`) and the cleaners for untrusted data from the internet (`cleanText`, `cleanNumber`, `cleanSharedCharacter`).
- `dice.html` — the **dice roller** (was `index.html`): modifiers, multiple dice, d100, advantage/disadvantage on a single d20, roll history.
- `character.html` — **characters**, with three views:
  - **Roster**: every saved character (any number per browser). Saved in `localStorage` key `"characters"`. An older single character under key `"character"` is migrated automatically.
  - **Guide levels** (`character.html?guide=beginner|intermediate|advanced`, optionally `&return=ai-dm.html`): *Beginner* shows ONE step at a time with a plain-language lesson and Back/Next (Next waits until the step is complete); *Intermediate* shows every step on one page with a one-line tip; *Advanced* is the normal page with no tutorial. `return` is only honored for `ai-dm.html` and `join.html`; after creating, it goes back there with `?hero=<id>`.
  - **Two classes (multiclassing)**, SRD "Multiclassing": step 2b is optional. A two-class hero starts at level 2+ (you only gain a second class when you level up) and splits levels between them; needs 13+ in each class's Primary Ability (`primary` / `primaryAnyOne` on each class in `rules.js`; Fighter needs Str OR Dex), checked on the scores step against final scores. Saved as `secondClass` + `secondClassLevel` (`level` stays the TOTAL level). Rules in `rules.js`: `getClassLevels`, `classSummary`, `getMulticlassProblems`, `getHitDiceText` (same-size dice pooled), `getMaxHp` (first class's full die only at level 1), proficiency from total level, saving throws and Unarmored Defense from the FIRST class only, a Bard/Ranger/Rogue second class gives one extra skill. On the sheet, "Level up / down in" picks which class gains the level, and another class can be added later (blocked with a reason if the 13+ rule isn't met). NOT applied: multiclass spell slots, Extra Attack stacking, class features above level 1, the exact proficiencies (armor/weapons) gained from the second class (not listed).
  - **Creator**: 7 steps by the 2024 rules: class, species, background (background gives the ability score bonus: +2/+1 or +1/+1/+1), ability scores (all three SRD methods: Standard Array, 4d6-drop-lowest, or Point Cost with 27 points and scores 8–15 via [−]/[+] buttons; the first two are assigned to abilities from a pool), skills (class choices + species choice + free background skills), review with a "what's missing" list.
  - **Special item** (on the sheet, after creation): each character can have one special item, stored as `character.specialItem` = `{ source: "srd" | "custom", name, type, rarity, attunement, appearance, powers }`. Pick one of 19 SRD Common/Uncommon magic items from `MAGIC_ITEMS` in `rules.js` (the player writes what it looks like, since the SRD gives only powers), or invent one: name, kind, looks, powers. Change/remove any time.
  - **Sheet**: HP, AC, initiative, speed, proficiency, passive Perception, hit dice, ability modifiers, saving throws (class proficiencies), skills, features, inventory. Level 1–20 with max HP recalculated by the rules. Roll with Normal/Advantage/Disadvantage.
- `dm.html` — the **DM** page. Purple theme via `<body class="dm">`. Panels:
  - **📣 Request players** (live game): "Open a game" creates a 6-character game code (alphabet without 0/O/1/I) and registers it with PeerJS as `dndtable-<CODE>`. Players' requests appear with their name, class, AC, HP and item; the DM **Accepts** or **Declines**. Accepted players join the party (with a 🟢 online / ⚪ offline dot, `remoteKey` = their unguessable browser id + character id) and a player who was accepted before comes straight back in. The DM keeps official HP: Damage/Heal in the party pushes `{type:"hp"}` to that player. "Table talk" feed shows joins, rolls and messages; the DM can announce to everyone. Messages are small objects with a `type`: player→DM `request`, `update`, `roll`, `say`; DM→player `waiting`, `accepted`, `declined`, `announce`, `hp`, `closed`. Everything received is validated with `cleanSharedCharacter`/`cleanText` and shown only with `textContent`; commands other than `request` are ignored from connections that weren't accepted. Closing the page ends the game (nothing is stored online). The invite link uses the helper's Wi-Fi address (`/api/status` → `lan`) or a hosted address.
  - **🎙️ Voice chat** (inside Request players): the DM presses "Start voice chat" (messages `{type:"voice", on}`; players who join later are told too). A player who sees the box presses "Join voice chat", which asks for the microphone and sends `{type:"voice-ready"}`; only then does the DM's browser ring them with a PeerJS audio call (`peer.call`) and only for accepted players. The player's browser only answers calls from the DM's peer id. Topology: everyone calls the DM; the DM's browser **mixes with Web Audio** so each player hears the DM plus all the other players but not themselves (mix-minus: one `MediaStreamDestination` per player). Mute buttons on both sides; leaving or stopping turns the microphone off. Players send `voice-leave` when they leave. Tested with two tabs and a generated tone as a pretend microphone: sound reached both ends at full level, and microphones stopped on leave/stop. NOT tested: three or more people at once, real microphones, echo (headphones recommended), phones/Safari. Audio needs https or localhost.

  - **The Party**: name, AC, HP (saved in key `"party"`). "📥 Import from saved characters" pulls in everyone from the Characters page (AC, max HP, passive Perception) and refreshes them on re-import without resetting tracked HP. Each imported player's special item shows under them (click to read its look and powers). "⚔️ Fight" copies a player into the initiative tracker; HP stays in sync both ways via `partyId` and `setPartyHp()`.

## Known limits (be honest about these)
- **Only a few options per list so far.** SRD 5.2.1 has 12 classes and 9 species (all included), but only 4 backgrounds (Acolyte, Criminal, Sage, Soldier). Spells, equipment, subclasses, class features beyond level 1, and feats are not built yet; features are listed by name only.
- **Rules data was proofread on 2026-11-21** against the official SRD 5.2.1 PDF (https://media.dndbeyond.com/compendium-images/srd/5.2/SRD_CC_v5.2.1.pdf): all 12 classes (hit die, saves, skills, level 1 features, Unarmored Defense), 9 species (size, speed, traits), 4 backgrounds, Standard Array, level 1 HP, HP per level and the proficiency bonus table match. Fixed then: Dragonborn *Draconic Flight* and Goliath *Large Form* are level 5 traits, and background tool proficiencies were added.
- **Special item effects are partly automatic.** 7 of the 19 SRD items have an `effects` entry in `MAGIC_ITEMS` that the sheet applies: Cloak of Protection (+1 AC, +1 all saves), Shield +1 (+1 AC), Gauntlets of Ogre Power (Str at least 19), Headband of Intellect (Int at least 19), Cloak of Elvenkind (Stealth rolls get Advantage automatically; cancels Disadvantage), Slippers of Spider Climbing (climb speed), Boots of Striding and Springing (speed at least 30). Items that need attunement have an "Attuned" checkbox (on by default); unattuned items apply nothing (SRD rule). Use `getAbilityScore`, `getAc`, `getSpeed`, `getSaveBonus`, `itemGivesAdvantage` (in `rules.js`) instead of reading `character.abilities` / `character.ac` directly, so item effects are never skipped. `character.ac` is the AC from armor ("base"); the total is `getAc(character)`, and the DM import uses the total.
- **Everything else about items is text only.** The other 12 items' powers (spells, charges, healing, the +1 weapon bonus, and so on) are described but not applied; attunement is not limited to a number of items; custom items have no automatic effects. Items are normally awarded by the DM; the app lets players pick freely. The 19 listed items were summarized from the SRD 5.2.1 "Magic Items A–Z" chapter; more can be added to `MAGIC_ITEMS`.
- **Rules the app doesn't apply yet:** multiclass spell slots and the starting proficiencies a second class grants (see above); Rogue *Expertise* (doubles proficiency on two skills); Elf *Keen Senses* is handled but other species/class features are listed by name only, with no automatic effect; class features above level 1 are not listed.
- **AC** starts as unarmored AC (10 + Dex, or the Barbarian/Monk version). The player edits it for armor.
- **No real privacy for the DM page**: "DM only" is just a separate page. Real privacy would need logins.
- **Saved data lives in one browser.** The DM's "Import from saved characters" only finds characters saved in the same browser. Live games send the needed details over the internet (PeerJS) instead.
- **Opening files from Finder (`file://`)**: some browsers keep separate `localStorage` per file, which would stop pages sharing characters. Use `ruby server.rb` and http://localhost:8787 so all pages share storage. The AI Dungeon Master requires the helper server.
- **Live games**: the connection is direct browser-to-browser (encrypted), but a free public PeerJS matchmaking service (0.peerjs.com) sees game codes and connection metadata, and its availability isn't guaranteed. Players need to open the app on their own device: same Wi-Fi via `ruby server.rb --share`, or put the app online later (GitHub Pages). Closing the DM's page ends the game; players reconnect with the code. PeerJS itself throws a harmless console `TypeError` if a peer sends `null`. The PeerJS script is pinned by version but has no integrity (SRI) hash.
- **AI Dungeon Master**: uses real money on the user's API key; only works on the computer running the helper; the AI tracks HP in the story only (the sheet isn't updated automatically); only the last 40 messages are sent. Costs/behavior were tested against a FAKE Claude server (request shape, errors, refusal, security checks), not the live API, because no key was available to the assistant. The first real run should be watched (model `claude-opus-5-5`, beta header `server-side-fallback-2026-07-01`; if the API rejects either, set `AI_DM_NO_FALLBACKS=1` or `AI_DM_MODEL=...`).

## Testing
- Claude's browser preview can't serve the project folder directly (macOS blocks Ruby from reading `~/Documents` there). Copy the files to the scratchpad and run `server.rb` from the copy; a preview config with just `{ "name", "port", "url" }` attaches to an already-running server.
- To test the AI without a key: run a fake Messages API that records requests (the `AI_DM_UPSTREAM` env var points `server.rb` at it) and start the helper with a dummy `ANTHROPIC_API_KEY`.
- Live games can be tested with two browser tabs on http://localhost:8787 (one DM, one player); they share `localStorage`, so use a different `cachedClientId` in one tab to simulate a second player.
- Everything was tested that way, with rule calculations checked by hand. Voice chat can be tested without microphones by replacing `navigator.mediaDevices.getUserMedia` in each tab with an `OfflineAudioContext`-free `AudioContext` oscillator → `MediaStreamDestination` stream, then measuring RMS with an `AnalyserNode` on each side.
